# 高仿"一木记账"可行性分析与技术方案

> App 定名：中文「**一笔一记**」，英文 **`penned`**。目标：Android 单端、无自建服务端（去中心化/本地优先，唯一例外是纯静态的更新检查）、体积小性能好、功能对齐一木记账、付费功能全免费、LLM 接入截图导入等智能功能。**语音记账明确不做**：各输入法自带语音转文字，转出的文字直接走"一句话记账"。

## 一、结论（TL;DR）

**可行，且比想象中更可行。** 理由：

1. 一木记账的付费功能里，**绝大部分本质是"本地功能"**（数量限制解锁、主题、统计、小部件、计算器类），没有任何需要服务端才能实现的魔法，全部可以本地免费实现。
2. 它真正依赖服务端/算力的只有截图 AI 识别、一句话记账的 NLP、云同步三样。前两样用"本地 OCR + 规则引擎 + 用户自带 LLM Key（BYOK）"即可覆盖且成本趋近于零；云同步用 WebDAV/局域网 + 操作日志合并可以做出"去中心化版"，隐私还更好。语音记账不做——输入法语音转文字 + 一句话记账已覆盖同一场景，还省掉一个 40MB 级离线 ASR 模型。
3. 十年记账数据在 SQLite 里也就几 MB，"小而快"的约束对记账类 App 天然友好。
4. 主要风险不在技术，而在**法律边界**（不抄资源/名称/UI 素材）和**工作量**（全功能约 3~6 个月业余时间，MVP 4~6 周）。

## 二、法律与合规边界（先说清楚，决定怎么做）

"高仿"在法律上可行的姿势是**仿功能，不仿表达**：

| 行为 | 判定 |
| --- | --- |
| 重新实现相同/相似功能（记账、统计、导入导出…） | ✅ 合法，功能本身不受著作权保护 |
| 参考交互思路（记账页布局逻辑、手势） | ✅ 合法 |
| 反编译 APK、抽取其代码/图片/图标/插画/文案复用 | ❌ 著作权侵权，且是"抄资源"最容易坐实的一类 |
| 使用"一木记账"名称、Logo、近似图标 | ❌ 商标侵权/不正当竞争 |
| 像素级复刻 UI 并公开分发 | ⚠️ 风险区；自用无人追究，公开分发应做自己的视觉表达 |

落地建议：
- **不反编译、不扒资源**。功能清单对着权益表 + 自己截几张图做"信息架构参考"即可，UI 全部自绘（开源图标库 Material Symbols / Iconify，配色自选）。
- 换名字（当前仓库名 `penned` 就不错），图标自己设计。
- 自用 + 开源分发都安全；不建议上国内应用商店蹭原品关键词。

## 三、功能盘点与拆解（基于《一木记账权益.md》）

把会员表翻译成工程视角的四个桶：

### A. 核心记账（免费部分，MVP 必做）
- 手动记一笔：支出/收入/转账，一级+二级分类，多账户，备注，日期
- 流水列表（日分组）、搜索、回收站、编辑/删除
- 单账本、1 个周期记账、1 个模板记账
- 统计：月/年报表、饼图、趋势图、收支排行
- 总预算、分类预算（3 个）
- 数据导入导出（CSV/Excel）、密码锁

### B. "数量限制"类会员功能 → 解锁=去掉限制，纯本地逻辑
多账本、周期记账/模板/愿望清单/二级标签/账单组合/分类预算/分期房贷/理财账户 不限数量、数据小卡片不限量。
**工程含义：数据模型一开始就按"无限量"设计，根本不用写限制代码。** 这是"免费化"里最便宜的部分。

### C. 智能类会员功能 → 用"本地优先 + BYOK LLM"实现
- 截图导入（50/日）+ AI 截图识别 → 见第五节管线
- 语音记账 → **明确不做**：输入法自带语音转文字已覆盖，转出的文字直接走"一句话记账"管道
- 一句话记账 → 本地 NLU 解析器 + LLM 兜底
- 智能标签 → 规则表 + 本地小分类器（KB 级，随使用自学习）
- 自动记账（20 次）→ `NotificationListenerService` 监听微信/支付宝到账通知，本地解析后弹确认卡片，**完全免费且无限次**

### D. 系统集成/定制类会员功能 → 原生 Android 一等公民能力
- 桌面小部件（Glance）、桌面记账（TileService 快捷磁贴 + App Shortcuts）
- 悬浮球记账、悬浮窗对账（系统悬浮窗权限）
- 多主题、图标自定义、首页数据自定义、自定义统计、统计模块设置
- 附件上传（压缩后本地存）、自定义小票（渲染 Bitmap 分享）
- 分期房贷（等额本息/本金计算器）、信用卡年费、账户分组、标签隐藏、精准导出
- **云同步 → 去中心化方案**（见第六节）
- **多人记账 → 降级为"共享账本合并"**（见第六节）

### 需要 LLM 的功能全景
| 功能 | 免费实现路径 | LLM 必要性 |
| --- | --- | --- |
| 截图导入 | 本地 OCR + 分版式规则引擎 | 兜底（难样本才调） |
| AI 截图识别 | 多模态 LLM（BYOK） | 必须，但用户自带 Key |
| 一句话记账 | 时间词+金额正则+分类关键词表 | 可选兜底 |
| 语音记账 | 不做（输入法语音转文字 → 一句话记账） | — |
| 智能标签 | 规则 + 本地增量分类器 | 不需要 |
| Excel 导入 | 本地解析微信/支付宝账单格式 | 不需要 |

## 四、技术选型

### 推荐方案 A：原生 Kotlin + Jetpack Compose（★ 选这个）

| 维度 | 评价 |
| --- | --- |
| 体积 | R8 压缩后核心 APK 可控在 **6~8MB**（OCR/ASR 模型按需下载，不打进 APK） |
| 性能 | 冷启动 < 500ms、内存 < 150MB 轻松达成；图表 Canvas 自绘万级数据无压力 |
| 系统能力 | 小部件、悬浮窗、通知监听、快捷磁贴、SAF、备份全部**第一方 API**——一木付费功能恰恰重仓这些 |
| 本地存储 | Room/SQLite 最成熟 |
| 风险 | 图表库要自己挑（Vico）或部分自绘；只要 Android（正好是需求） |

### 备选方案 B：Flutter
UI 迭代快、fl_chart 生态好；但 APK 基础体积 10MB+，且悬浮窗/小部件/通知监听/无障碍全要走 platform channel 手写插件——对"小而全 + 系统集成重"的目标反而更费劲。**只有未来要上 iOS 时才值得换 B。**

### 备选方案 C：KMP + Compose Multiplatform
逻辑层跨端、UI 共用。单人项目提前付 iOS 复杂度不值，列为未来演进项。

### 关键依赖清单（方案 A）
- UI：Compose + Material 3、Navigation、Glance（小部件）
- 数据：Room + DataStore；附件用 Coil 展示 + 自管文件目录
- 图表：Vico 或 Canvas 自绘（饼图/柱状/折线/热力）
- OCR：ML Kit Text Recognition v2 中文**bundled 版**（不依赖 GMS，模型 ~12MB 改为首次使用下载）或 PaddleOCR-mobile（中文效果更稳）
- LLM：OkHttp/Retrofit 直连 OpenAI 兼容接口（BYOK，见第五节）
- 更新检查：OkHttp 拉静态清单 + DownloadManager/OkHttp 下载 + FileProvider 安装（见第七节，全 App 唯一服务端功能）
- xlsx：导出用轻量方案（CSV 为主，xlsx 可用 fastexcel 或手写最小 zip+xml）
- 同步：自研 op-log 合并（第六节）+ WebDAV（sardine-android）

## 五、LLM 接入设计（截图导入等智能功能）

### 核心决策：BYOK（用户自带 API Key），应用不含任何服务端
- 设置页支持配置：`base_url` + `api_key` + `model`（OpenAI 兼容格式）
- 预置推荐档位：GLM-4V-Flash（**免费**）、qwen-vl-flash（每张截图 < 1 分钱）、DeepSeek/Kimi 等文本模型用于一句话记账
- 隐私故事比官方还强：数据不出设备，LLM 调用用户知情、可关

### 截图导入管线（三级降级，成本从 0 开始）
```
图片入口（相册/分享/拍照）
  → 压缩（长边 1280）
  → ① 本地 OCR（ML Kit/PaddleOCR，离线、毫秒级、免费）
  → ② 版式识别：关键词特征判断来源（微信支付/支付宝/美团/京东/银行 App）
  → ③ 结构化抽取：每来源一组规则模板（正则金额/时间/单号 + 键值定位）
       命中 → 直接生成"待确认账单"
       未命中/低置信 → ④ 调多模态 LLM（BYOK），要求输出严格 JSON schema
  → 本地校验 + 分类映射（关键词/embedding 匹配内置分类树）
  → 用户确认卡片（金额可改、账户可映射）→ 入库
```
- 规则引擎覆盖 80%+ 常见版式（微信/支付宝支付成功页版式极其稳定），LLM 只兜底，**日常成本≈0**
- LLM prompt 设计：输出 JSON（收支类型、金额、商户、时间、支付方式、单号），本地 schema 校验，分类映射在本地做（LLM 不决定分类 ID，避免幻觉）
- 批量导入：微信/支付宝官方导出的 Excel/CSV **本地解析**即可，不需要 LLM，做字段映射 UI

### 一句话记账
- 本地解析器：日期词解析（"昨天/上周三"）+ 金额正则 + 可编辑分类关键词表 → 置信度
- 低置信 → BYOK 文本模型（每条几厘钱）→ 同样 schema 校验 + 本地分类映射

### 语音输入（不做独立功能）
- 一句话记账的输入框接受任意来源文本：键盘输入、输入法的语音转文字、剪贴板粘贴均可
- 应用内不集成 ASR：避开 `SpeechRecognizer` 在无 GMS 国产 ROM 上的兼容性问题，也省掉离线 ASR 的模型体积

### 自动记账（把会员 20 次/日 变成免费无限次）
- `NotificationListenerService` 监听微信/支付宝通知 → 本地正则解析到账消息 → 通知栏确认卡片 → 一键入账
- 全本地、零成本、无次数限制

## 六、去中心化同步设计（替代"云同步"+"多人记账"）

### 数据模型为同步而生
- 所有业务表：`uuid` 主键 + `updated_at` + `deleted`（软删）+ `device_id`
- 变更写 outbox（事件日志）；**余额、统计一律从流水重算，不落库** → 冲突面几乎消失

### 同步载体（无自建服务端）
1. **本地备份/恢复**（文件级，必做）：每日自动导出加密 JSON 到 SAF 用户目录
2. **WebDAV**（坚果云免费额度足够用十年）：上传 op-log 增量包 + 定期全量快照，按设备水位游标合并，幂等 apply + 字段级 LWW
3. **局域网直连**：mDNS 发现设备 → HTTP 直传 op-log（换机/夫妻双机秒级同步）
4. **手动文件搬运**：`.penned` 导出文件即同步包

### 端到端加密
op-log 打包 AES-GCM，密码用户自持；连网盘服务商都看不到账目。

### 多人记账的降级
真·实时协同（WebSocket 服务端中转）与"不做服务端"矛盾 → 降级为**共享账本合并**：家庭成员共用同一 WebDAV 目录/定期互传合并包，最终一致（延迟分钟级）。**这是本方案里唯一的功能性妥协，建议 v2 再做。**

## 七、应用内更新（全 App 唯一的服务端功能）

定位：**没有后端代码的"服务端"**——只有静态文件托管，无鉴权、无数据库、无用户数据上报，零运维成本。用户可在 app 内"检查更新并下载"；不做厂商级推送通道，靠轻量轮询（手动/低频自动检查）即可满足需求。

### 托管形态（可组合，按序回退）
| 方案 | 说明 | 成本 |
| --- | --- | --- |
| GitHub Releases + 仓库内 `update.json`（首选，配合开源） | 清单进仓库（raw/gh-pages），APK 挂 Releases | 0 |
| Cloudflare R2 + 自定义域 | 国内直连稳定的静态托管，10GB 免费额度 | ≈0 |
| 任意静态托管（OSS/COS 等） | 作为清单 `urls` 里的备用镜像 | ≈0 |

### 清单格式 `update.json`
```json
{
  "versionCode": 12,
  "versionName": "1.2.0",
  "minVersionCode": 5,
  "changelog": ["新增：截图导入", "修复：…"],
  "sha256": "<apk 摘要>",
  "size": 8123456,
  "urls": ["https://primary.example/…apk", "https://mirror.example/…apk"]
}
```
- `urls` 多镜像按序回退，解决国内 GitHub 直连不稳
- `minVersionCode` 只升级文案「强烈建议更新」，**从不强制**（D059；本文早期写的"强制更新"已作废）
- **2026-10-18 增补（D114）**：预发布通道另有一份 `update-prerelease.json`；清单追加可选
  `channel` / `publishedAt` / `tag`。正式版只读 `update.json`，预发布订阅读预发布清单（正式地址兜底）；
  通道是客户端 DataStore 里的订阅，beta 用户升正式版后不降级。实现口径以 `docs/specs/M2.md` 与
  D058/D059/D061/D064/D114 为准（本文的 DownloadManager、强制更新等早期选项未采用）

### 客户端流程
1. 触发：设置-关于 手动"检查更新"；可选启动时自动检查（本地记录上次检查时间，至多每天 1 次，静默无新版不弹窗）
2. GET 清单 → 比较 `versionCode` → 新版则展示 changelog 对话框
3. 下载：DownloadManager（系统通知栏进度）或应用内 OkHttp 流式下载，多 url 依次回退，支持断点续传
4. 校验：SHA-256 对比清单摘要 + **新 APK 签名必须与当前安装签名一致**（防镜像/CDN 被篡改），任一不符即中止并提示
5. 安装：FileProvider + `ACTION_INSTALL_PACKAGE`，首次引导授予"安装未知应用"权限（`REQUEST_INSTALL_PACKAGES`）
6. 隐私：请求只打到静态文件，不携带任何用户标识——去中心化承诺不被破坏

### 工程注意
- **签名密钥自更新上线起终身固定**：新 APK 签名必须与已装一致，keystore 一旦丢失或更换，自更新链路即断——务必离线备份
- `versionCode` 单调递增并与构建流程绑定，避免手改出错
- 更新检查排在 M1 之后（M2）：先建立"能自己迭代"的通道，再进入功能密集期

## 九、体积与性能预算

- APK：核心 **< 8MB**（OCR ~12MB 模型首次使用时下载，不打包；无 ASR 依赖）
- 冷启动 < 500ms；内存 < 150MB
- 存储：纯账目数据十年 < 10MB；附件长边 1280/WebP 压缩后每张 100~200KB，提供"不存原图"开关
- 列表：Room + Paging + LazyColumn；图表先按日/周聚合再画，万级流水无压力

## 十一、产品建议

- 定名「一笔一记 / penned」：谐音呼应"一木"但用字完全不同，与"一木记账/木木记账"商标冲突风险低；上架前建议在商标网查重一次
- UI 致敬信息架构（布局逻辑），视觉自绘：配色、图标（Material Symbols）、插画、动效全部自己的表达
- 建议开源（GPL-3.0/AGPL 或 MIT）：BYOK、去中心化、无广告的本地记账是开源社区喜欢的题材，能白嫖共建（尤其截图规则引擎的版式适配）
- "免费 + BYOK"的故事讲出来就是卖点：官方 AI 收费，你这里**用户自己的 Key 自己定价，甚至免费**（GLM-4V-Flash 免费）
