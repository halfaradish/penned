## 二、交付口径（所有切片共同遵守）

1. **一次迁移建表**：v8→v9 建 `keyword_rules` 与 `pending_entries` 两表，并给既有表补三处列——`transactions.externalId`（外部单号，账单去重用）+ 索引、`import_batches.sourceKind / skippedCount / duplicateCount`（批次来源与"跳过/重复"计数）；全部带同步字段，后续切片不再升版本；`9.json` 入库 + `MIGRATION_8_9` + migration 测试。顺带把 `PennedCsv` 的导出/导入补上 `externalId` 列（旧文件缺列按空处理，向后兼容）。**`externalId` 的索引是非唯一的**（去重在导入侧做；唯一约束会把"同一份账单导两次"变成插入失败，而不是可解释的"重复 N 条"）。**唯一例外**：`TxSource.NOTIFICATION` 只是枚举加值——`source` 列本来就是 TEXT + 转换器按 `.name` 存（`Converters.txSourceToString`），schema JSON 一字不变，**不算 schema 变更、不走迁移**。
2. **零新增依赖**（本规格最大的硬约束，比 M3 的"不新增"更硬——M4 原本最可能要引 OCR/序列化）：
   - 网络走既有 **OkHttp**（D058）；JSON 走平台 **`org.json`**（D058 先例：`UpdateManifest` 即此写法，不引序列化库）
   - 图片解码 / 缩放 / 压缩走平台 `BitmapFactory` / `Bitmap.compress`（不引 Coil 等图像库）
   - 相册走 `PickVisualMedia`（minSdk 26 自动回退到 SAF，**不需要读存储权限**）；拍照走系统相机 `MediaStore.ACTION_IMAGE_CAPTURE`（**不申请 CAMERA**）；分享收图走 `ACTION_SEND` + `image/*` intent-filter
   - 压缩包与 XML 走平台 **`java.util.zip` + `javax.xml.parsers`(DOM)**（`.xlsx` 读取；两条路线在 `-no-jdk` 单测与 Robolectric 下都已实测可用，见 附 B）；`.xls` 复用既有 `Biff8Reader`
   - → `gradle/libs.versions.toml` 一个字都不动；验收含"零新依赖"核对
3. **不引 WorkManager / AlarmManager / 前台服务 / 定时任务**（M3 §六 延续）。M4 唯一的后台形态 = `NotificationListenerService`（系统按需绑定、可随时在系统设置里撤销授权）；**不读短信、不装无障碍**。
4. **LLM 三原则**：
   - **BYOK**：用户自带 Key，应用不含任何服务端、不代理、不留存调用记录
   - **显式开关 + 显式触发**：AI 默认关；每张图、每句话调不调由用户点，绝不后台预跑
   - **分类与账户永远本地映射**：LLM 只许回 收支类型 / 金额 / 商户 / 时间 / 备注，**不许回分类或账户 ID**（防幻觉的唯一有效手段）
5. **BYOK 的服务地址只接受 `https://`**（裁决 C2）：`release` 的 `usesCleartextTraffic=false`，填 `http://` 是**当场报错**（页面给出可读原因），不是静默失败；局域网自建模型（http）不在本版范围内。
6. **四条入账路径共用一套底座**：`KeywordRules`（关键词 → 分类/标签，纯函数匹配）、`LlmClient`（文本与图像两用，同一份出参 schema）、**宽松金额解析**（`domain/MoneyParse.kt`，见 §二·7）、`识别结果 → 草稿` 的映射。**机器只填草稿，入账必须过用户确认**（一句话 = 就地结果卡；截图 / 通知 = 预填记一笔页；账单文件 = 预览页 + 批量入库）。
7. **金额一律经"宽松解析"纯函数换 Long 分**：既有 `Money.parseToCents` 是**输入框契约**（只吃 `^\d+(\.\d{1,2})?$`，不吃 `¥`/千分位/全角/`元`），**原样不动**；M4 新增 `MoneyParse.toCents(text): Long?` 到 `domain/`，负责「`¥1,234.56` / `1,234.56` / `１２３４`（全角）/ `12元` / `12块` / `-` / 空 / 非数字」，并在 **`M4-0`** 落地（一句话 / 账单行 / LLM 出参三个消费者都要它）+ 表驱动单测。数值来源（xlsx 的数值单元格、LLM 回的数字）按 `Math.round(v * 100)` 折分。**解析不出 = null（不猜）**；超过两位小数按四舍五入到分（真实样本全是两位，钉一条测试）。
8. **解析 / 匹配一律 domain 纯函数 + 表驱动单测**；通知文案样本用**脱敏 fixture 进仓库**（微信 / 支付宝各 ≥6 条），不得引用 `docs/local/` 的真实账单。
9. 新页面先补 `docs/界面规范.md` 逐屏版式（**从 §13·补三十一起编号**——补二十九 = D094~096、补三十 = D097~099 已占用），交付含 Roborazzi 浅/深基线 + `@Preview` 可渲染；隐私文案（"这张图将发给 X"、"Key 只存本机"、"原文不进 AI"）收敛到一处常量，不各页各写。
10. 模拟机走查照 M3 §二·7（`GxuDev` 只读/探针 或 `PennedM2`），走查前后核对库内"活跃 / 软删"条数；**通知监听用 `adb shell cmd notification post` 造通知验证**（不必依赖真实微信/支付宝）。
11. **开工顺序：9 片分 4 批（3+2+2+2）**（照 M3 §二·8）：批次一 = 底座（M4-0 / M4-1 / M4-2），批次二 = 文本与文件读取（M4-3 / M4-4），批次三 = 预览与 AI（M4-5 / M4-6），批次四 = 系统来源（M4-7 / M4-8）。**批次内可换序，批次间串行**；允许拆两次会话的片见 §三 各片标注（M4-4 / M4-5）。
12. **账单文件导入以本地解析为主干**：微信 / 支付宝两家用内置规则表（**代码常量，不落库、不热更新**）**完全不依赖 LLM**；LLM 只给"不认识的表头"与"没见过的商户"提速（R12），且始终是"建议值、用户可改"。通用模式（认不出的表头）靠列映射 UI 兜底，**没有 Key 也能导入**。
13. **外发边界**：账单文件与通知的原始内容**永不外发**；LLM 的输入只有 ① 表头行（默认只此一行）② 去重后的商户名 ③ 现有分类名。**金额、时间、交易单号一律不出设备**——写进验收（假服务器断言请求体里不出现这三样，且 `FakeHttpServer` 要扩成能读请求体，见 §三 M4-6）。
14. **分类一律不新建**（裁决 B1）：账单文件与识别结果里的分类线索**只按名字匹配账本里已有的分类；匹配不上留空**，交给关键词规则（M4-1）与 AI 建议（M4-6）补。既有**一木 xls 导入**的"缺则建"行为**不动**（那是自家词汇，不是平台词汇）——M4 走另一条不建的路径。
15. **账户可以新建**（裁决 F4/B2/B4）：支付方式对不上时按名新建账户，**类型按名猜**（花呗/白条/信用卡/京东金融 → 信贷；余额宝/零钱通/理财/基金 → 理财；其余 → 资金）并在预览页**可改**；掩码照留、各建一个（裁决 B3：不同卡号本就是不同账户）。映射表仍是默认路径（按名匹配），新建是兜底、不是取消映射。
16. **批量导入的重复与跳过必须可见**：重复（单号命中 / 疑似重复）与跳过（交易关闭 / 已退款 / 不计收支 / 坏行）在预览页**分列计数**，不静默丢；**每行只归一类**（优先级见 §三 M4-4），导入后批次可整体删除（既有能力）。
17. **候选池（`pending_entries`）的隐私口径**（裁决 C3）：**没有"解析失败"状态**——识别成功才落库、失败不落（当场报错可重试）；「清空已处理」= **硬删**（`DELETE`，`pending_entries` 是**非账目**的候选池，不入同步——本例外记入 decisions）；已入账的候选行保留 `rawText` 供回看"机器当时读到了什么"，但**不做"用户改过金额/日期后与原文不一致"的留痕**。
18. **通知提醒点击要过密码锁**（裁决 C4）：点通知进来的 intent **先暂存，解锁后补跳**到「待确认」页（既有 `LockGate` 只在冷启动/回后台时锁，新 intent 会被丢掉——这是本片要补的那个洞）。
19. **AI 默认关**（`llm_enabled` 默认 false）；未配置 Key 时所有 AI 入口给重定向（跳 AI 设置）而不是崩溃或空转；每条 AI 调用都是**用户点的那一下**。

#### M4-0 schema 地基 + 底座纯函数 + 智能设置项（v8→v9 一次迁移，无 UI）

- **入口**：无（本片零页面——只有表/列/索引/DAO/两个纯函数/设置键；页面从 M4-1 起）。

- **数据**
  - 新表 **`keyword_rules`**（关键词规则，与分类/标签同账本域——两者的目标都是账本内实体）：
    `id / bookId / keyword / targetType(CATEGORY|TAG) / targetId / priority / enabled / createdAt / updatedAt / deleted / deviceId`；索引 `bookId`。
  - 新表 **`pending_entries`**（机器识别候选池）：
    `id / kind(SCREENSHOT|NOTIFICATION) / sourceApp? / rawText? / type(EXPENSE|INCOME|TRANSFER|UNKNOWN) / amountCents? / occurredAtEpochMinute? / merchant? / note? / categoryId? / status(PENDING|ACCEPTED|DISCARDED) / txId? / createdAt / updatedAt / deleted / deviceId`；索引 `status`。
  - 老表补列（同一迁移，为 M4-4/M4-5 的账单导入铺路）：`transactions.externalId TEXT`（可空；微信"交易单号"/支付宝"交易订单号"，去重主键）+ **非唯一**索引 `(bookId, externalId)`；`import_batches.sourceKind TEXT NOT NULL DEFAULT 'YIMU'`（YIMU | PENNED_CSV | WECHAT | ALIPAY | GENERIC）、`import_batches.skippedCount INTEGER NOT NULL DEFAULT 0`、`import_batches.duplicateCount INTEGER NOT NULL DEFAULT 0`（旧批次默认全是 YIMU，语义不变）。
- **口径**：规则匹配 = 按 `priority` 升序取**第一条命中**（同优先级按 `createdAt`）；`enabled = false` 跳过；**空关键词拒绝入库**；匹配时去首尾空白、大小写不敏感（中文无大小写，英文商户名用得上）。候选池 `amountCents` 与 `occurredAtEpochMinute` **可空**（解析不出就是空，**不猜**）；清空已处理走硬删（§二·17）。
- **DAO**：`KeywordRuleDao`（按账本观察 / upsert / 软删 / 上下移 / 启停）、`PendingEntryDao`（插入 / 按状态观察 / 标记 `ACCEPTED` + 回填 `txId` / 丢弃 / **清空已处理 = 硬删**）、`TransactionDao.externalIdsInBook(bookId, ids)`（导入前的批量查重）。
- **纯函数**：`KeywordRules.match(text, rules): RuleHit?` —— 表驱动（优先级 / 多命中取先 / 禁用跳过 / 大小写 / 空关键词 / 二级分类与标签目标）；`MoneyParse.toCents(text): Long?` —— 宽松金额解析（§二·7，三个消费者共用）。
- **设置项**（`SettingsRepository` 同款 DataStore 键，照既有 `KEY_*` 私有常量写法）：`llm_enabled`（默认 **false**）、`llm_base_url`、`llm_api_key`、`llm_model`、`llm_vision_model`（空 = 跟 `llm_model`）、`auto_entry_enabled`（默认 **false**）、`auto_entry_packages`（逗号串，默认空 = 什么都不处理）。
- **`PennedCsv`** 导出/导入补 `externalId` 列（导出写在末尾列；导入按表头名取，旧文件缺列 = 空，往返幂等有测试）。
- **明确不做**：任何 UI（本片零页面）；`keyword_rules` 的正则/热更新（§六）；`pending_entries` 的自动过期清理（提案区）。

**对账方法（M4-5 验收用，两份都跑）**：两家导出在**文件头**自带声明——`共 N 笔`、`收入：a 笔 X 元`、`支出：b 笔 Y 元`、`不计收支：c 笔 Z 元`（微信写"中性交易"）。逐行重算的「将导入条数 / 支出合计 / 收入合计」必须与这四行对上。本次冻结前已按此方法实测两份样本**逐分对上**（重算不写进本稿，避免把个人数字入库）。

**读取层写法（M4-4 的依据）**：CSV 走 `CsvCodec`（已有）+ 编码探测；xlsx 走 `ZipInputStream` 取条目 + DOM 解析 + sharedStrings 下标解引用 + 序列日期换算 + `/` 归一 + 全字段 trim；xls 走既有 `Biff8Reader`；zip 走 `ZipInputStream` 取唯一 csv。会话量估计：**读取层 1~2 个会话，口径/去重 1 个会话**——所以 M4-4 允许拆两次会话（csv/xls/zip 一次、xlsx 一次）。

## 附 B：读取层路线预验证（本次冻结前实测，探针测试已删除）

- **编译期**：compileSdk 36 的 `android.jar` 里有 `java/util/zip/ZipInputStream|ZipOutputStream`、`javax/xml/parsers/DocumentBuilderFactory|SAXParserFactory`、`org/w3c/dom/Document`、`org/xmlpull/v1/XmlPullParser`、`android/util/Xml`——**`-no-jdk` 下编译不受 M2 那个 `com.sun.*` 问题的影响**。
- **运行期**：探针测试（临时写入 `app/src/test/.../probe/`，验证后删除、未留痕）确认：① `ZipOutputStream` 现场生成最小 xlsx → `ZipInputStream` 读回 → DOM 解析 sheet + sharedStrings，在**普通 JVM 单测**（`-no-jdk`）里跑通 ② 同一套在 **Robolectric**（`@Config(sdk = [35], qualifiers = "w400dp-h800dp")`）下也跑通，且 `android.util.Xml.newPullParser()` 可用（备选路线） ③ 序列日期 `46312.55502314815` → `1899-12-30 + round(serial×86400)` 秒 → 与样本里的时间**逐秒对上**；取整与四舍五入两条路线在**分钟口径上一致**。
- 结论：M4-4 的 xlsx 读取**不需要任何新依赖**，用 `java.util.zip` + DOM 即可，且能被单测覆盖（fixture 现场生成，仓库不落账单样本）。
