# 规格 M2：应用内更新（冻结 2026-10-10）

来源：可行性方案第七节（`update.json` 协议与客户端流程）+ 里程碑表 M2 行；决策 D012（release minify 与体积验收）、D013/D057（applicationId 终审）、D058（引入 OkHttp）、D059（从不强制更新）。

定位：**全 App 唯一的"服务端"**——只有静态文件托管，无鉴权、无数据库、无用户数据上报。目标是把"能自己迭代"的通道打通，此后每个版本都走自更新。

前置（已完成）：applicationId 定稿 `dev.penned.app` 并冻结（D057）；依赖批准（D058）。

## S1 `update.json` v1 协议

清单是纯静态 JSON，字段固定如下（v1 冻结；客户端容忍未知字段，新增字段不破坏旧客户端）：

```json
{
  "versionCode": 2,
  "versionName": "0.2.0",
  "minVersionCode": 1,
  "changelog": ["新增：应用内更新", "修复：…"],
  "sha256": "<apk 摘要，小写十六进制>",
  "size": 8123456,
  "urls": ["https://主地址/penned-0.2.0.apk", "https://备镜像/penned-0.2.0.apk"]
}
```

语义：
- `versionCode` > 本机 `BuildConfig.VERSION_CODE` → 有新版；`<=` → 已是最新
- `minVersionCode` **只做文案分级**（D059）：本机 versionCode 低于它时提示语升级为「强烈建议更新」，**不强制、不拦截、不重复弹**
- `changelog` 逐条展示（列表，可空）
- `sha256` / `size` 用于下载后校验；`urls` 按序回退，**至少 2 个**（主 + 备）
- 解析：平台自带 `org.json`（不引序列化库）；字段缺失或类型不符 → 视为清单无效（当作检查失败，不崩）

> **2026-10-18 修订（D114，协议 v1.1）**：追加三个**可选**字段——`channel`（`stable` / `prerelease`，
> 表示这次发布本身是正式还是预发布）、`publishedAt`（ISO-8601 UTC）、`tag`。缺 `channel` 的老清单仍有效；
> 认不出的 `channel` 值 = 清单无效。正式版客户端必须拒绝 `channel=prerelease` 或 `versionName` 含 `-` 的清单；
> 预发布订阅两者都收（正式版发布时预发布清单里装的就是正式版）。

### 清单与 APK 的托管
- 清单地址是客户端常量（`BuildConfig.UPDATE_MANIFEST_URLS` / `UPDATE_MANIFEST_URLS_PRERELEASE`，D114）：
  release 走已发布地址；debug 走本机测试服务 `http://10.0.2.2:8000/update.json` 与
  `…/update-prerelease.json`（模拟机连宿主，仅 debug 放行明文）
- **两条通道两份清单**（D114）：`update.json` 只由纯数字正式版流水写；`update-prerelease.json` 由每次发版覆盖
  （正式版发布时若 base 不低于预发布线也写它）。已装 0.1.0 只读 `update.json`——服务端隔离是它唯一防线
- 清单本身给 2 个候选地址按序回退（首发建议：主 = 国内可达静态托管，备 = GitHub raw）；预发布先读自己的清单，
  再拿正式清单地址兜底
- **托管渠道在首发时定**（方案第七节三选一：GitHub Releases+仓库内清单 / Cloudflare R2+自定义域 / 任意静态托管）。约束：**首发渠道必须国内可达**（`raw.githubusercontent.com` 仅作备选，不作唯一）；渠道只需给出静态文件 URL，客户端不关心用的是哪家
- 清单文件本身进仓库（便于审计与手改）；APK 不进仓库

## S2 检查流程（UpdateChecker）

- **手动检查**：我的 → 关于 → 「检查更新」。任何结果都要有反馈（有新版 → changelog 弹窗；已最新 → 一句话；失败 → 失败原因）
- **启动自动检查**：每天至多一次（DataStore 记 `lastCheckAt`，**仅在成功拿到并解析清单后**才写）；无新版静默；有新版弹一次 changelog 弹窗（可取消）
  - `notifiedVersionCode` 也进 DataStore：**同一个 versionCode 只自动提示一次**，不重复骚扰（手动检查不受此限）
  - ~~关于页给「启动时自动检查更新」开关，默认开（方案原文"可选启动自动检查"）~~ → **2026-10-10 修订（D064）**：开关下线，**自动检查恒为开**（用户裁决「现在默认自动检查，开关放到后期的工程中」；`SettingsRepository.autoUpdateCheck` 的键与读写方法保留待接回）
  - **2026-10-18 修订（D114）**：关于页新增的是**通道开关**「接收预发布版本」，与自动检查无关；自动检查仍恒为开
- **通道选择（D114）**：订阅状态存 DataStore（`update_channel` / `update_channel_explicit`），**不看当前版本名**。
  首次启动按安装包初始化；用户显式选择优先；正式版包上手动装 beta 自动升舱；**beta 用户升正式版不降级订阅**
  （所以 `0.2.0-beta.1 → 0.2.0` 之后仍能收到 `0.3.x-beta`）。正式订阅读 `update.json`，预发布订阅读
  `update-prerelease.json`（正式地址兜底）
- **网络**：连接超时 10s、读取超时 15s；多候选清单地址按序回退（前者失败才试后者），全部失败 → 失败态
- **隐私**：请求只打静态文件，**不带任何查询参数、不携带设备/用户标识**；User-Agent 固定 `penned-update/<versionName>`
- 检查中不阻塞 UI；同时只允许一个检查在跑（重复点"检查更新"复用当前结果）

## S3 下载（UpdateDownloader）

- **应用内 OkHttp 流式下载**（不用 DownloadManager，D058）；目标 `cacheDir/updates/penned-<versionCode>.apk`
- **断点续传**：临时文件已存在且小于清单 `size` 时带 `Range: bytes=<已有长度>-` 续传；服务端回 200（不支持 Range）则从头覆盖写
- **进度**：回调「已下载 / 总大小」，UI 画进度条与百分比
- **取消**：用户可取消；取消后**保留**临时文件（供下次续传），并提供"重新下载"（重新下载时按续传规则走）
- 下载**必须由用户点了才开始**（不自动下载、不后台下载、不引 WorkManager）
- 超时：连接 15s、读取 30s；失败可重试（重试即续传）

## S4 校验（DownloadVerifier）

下载完成后、安装之前，两道校验都必须过：
1. **大小 + SHA-256**：对整文件流式计算（续传场景下必须整文件重算，不能增量拼）——与清单 `sha256` 逐字符比对（忽略大小写）
2. **APK 签名必须与已装版本一致**：API ≥ 28 用 `GET_SIGNING_CERTIFICATES` / `apkContentsSigners`，API 26~27 退回 `GET_SIGNATURES` / `signatures`；逐证书比对字节（比对逻辑抽纯函数）
   - 理由：防镜像/CDN 被篡改（方案第七节）

任一不符 → **删除已下载文件**、给一句可读原因（如「安装包校验失败，已删除」）、状态回失败态。

## S5 安装（UpdateInstaller）

- `FileProvider`（authority `dev.penned.app.fileprovider`，`res/xml/file_paths.xml` 暴露 `cache-path` 的 `updates/`）→ content URI
- 启动安装：`Intent(ACTION_VIEW)` + `setDataAndType(uri, "application/vnd.android.package-archive")` + `FLAG_GRANT_READ_URI_PERMISSION`
- Android 8+ 未授权"安装未知应用"时（`canRequestPackageInstalls()` 为 false）：先弹一句说明（为什么需要、装了才会更新），再 `ACTION_MANAGE_UNKNOWN_APP_SOURCES` 引导到系统设置；**这一步也可取消**（D059）
- Manifest 声明 `REQUEST_INSTALL_PACKAGES` 与 `INTERNET`
- 装完不自动重启 App、不做"重启"按钮：用户从系统安装器点「打开」进来即新版本

## S6 关于 / 更新页 UI

- 入口：我的页「关于」行（现为不可点信息行）改为可点 → 路由 `about`；副标题显示真实版本（读 `BuildConfig.VERSION_NAME`，**去掉 `MineScreen` 里硬编码的「版本 0.1.0（M1）」**）
- 页面内容：品牌头（App 标记 + App 名 + 定位语）+ 版本 / 更新卡 + 页脚隐私一句话（「更新检查只访问静态文件，不携带任何标识」）；**2026-10-10 修订（UI-16/D064）**：版面按 QQ / 微信的关于页重做——品牌头走极淡单色渐变底、版本与更新收成一张卡的两行（`当前版本` 信息行 + `检查更新` 整行入口）、状态机收进「行尾摘要 + 需要动作时才展开的详情块」（Idle 的铺满按钮退场）；逐屏版式见 `docs/界面规范.md` §13·补十一
- **2026-10-18 修订（D114）**：版本卡在「当前版本」与「检查更新」之间加一行「接收预发布版本」开关（`PennedSwitchRow`），副标题「开启后会收到 dev / test / beta；正式版更新不受影响」；切换会清掉旧清单并让下一次检查按新通道重来。这是**通道开关**，不是已下线的自动检查开关
- 更新区状态机：`idle`（整行可点）→ `checking` → `upToDate`（已是最新，显示检查时间）→ `available`（新版本号 + changelog + 「下载」按钮；低于 minVersionCode 时文案为「强烈建议更新」）→ `downloading`（进度条 + 百分比 + 取消）→ `verifying`（行尾「校验中…」）→ `ready`（「去安装」按钮）→ `error`（原因 + **唯一动作**「重试」——`retry()` 手上有清单就续传下载、没清单就重新检查；重新拉清单也可直接点上面那行「检查更新」，2026-10-11 修订 D065）
- 弹窗：changelog 弹窗与"强烈建议"提示**一律可取消、可返回键关闭**（D059）
- 版式与 token 走 `docs/界面规范.md`（新增"关于/更新页"一节）

## S7 发布工程

- **版本号单一来源**：仓库根 `version.properties`（`versionCode` / `versionName`），`app/build.gradle.kts` 读取（替掉硬编码）；`./gradlew bumpVersion -PversionName=x.y.z` 自增 versionCode（工作流第五节 E：禁手改）。**2026-10-18 修订（D114）**：预发布写 `x.y.z-beta.1` 一类；`bumpVersion` 校验 `x.y.z` / `x.y.z-suffix` 两种形态，其余直接失败
- **签名**：`signingConfigs` 从 `local.properties` 读（`penned.storeFile` / `penned.storePassword` / `penned.keyAlias` / `penned.keyPassword`）；**keystore 放仓库外**，`.gitignore` 补 `*.jks` / `*.keystore` / `penned-release.*`；keystore **终身固定 + 离线备份**（D057/D059 的工程底线）
- **release 构建**：打开 `isMinifyEnabled` + `isShrinkResources`（D012），按需补 `proguard-rules.pro` keep 规则；**体积验收 < 8MB**（当前未签名 release 8.97 MiB，基线记录在 board）
- **清单生成**：`./gradlew makeUpdateJson` 从签名 APK 算 `sha256`/`size`，`-Pchannel=stable|prerelease` 与 `-Pout=…`
  指定通道与产物（changelog 由参数提供）；发布流程：bump → changelog → annotated tag → 签名 APK →
  `makeUpdateJson` → 建 Release → 清单提回 main → 旧版本走应用内更新验一遍闭环
- **双通道流水（D114）**：正式 tag 只写 `update.json`，同时在不倒退时覆盖 `update-prerelease.json`；预发布 tag 只写
  `update-prerelease.json`，Release 标 `--prerelease`；每次发版 `versionCode` 必须大于两份清单最大值，tag 必须在 main 上；
  旧线 hotfix（正式版 base 低于预发布线）只写正式清单。细节见 `.github/workflows/release.yml` 与
  `.github/scripts/release_channels.py`（带 `--self-test`）
- **release 回归方式**：D017 已禁 release 单测 → 回归 = debug 单测全绿 + release 包在一台干净 AVD 上功能走查（minify 后的真包）

## 不做清单

- **强制更新**（不可取消弹窗 / 拦截使用 / 反复提示）——本 App 从不强制（D059）
- 静默自动安装、自动下载（下载必须用户点）
- 增量/差分更新（差分包生成与合并）
- DownloadManager、WorkManager / 后台定时检查（只在启动与手点时检查）
- 多渠道 / 灰度 / A-B、应用商店上架、崩溃上报等一切"带服务端味"的东西
- 更新检查携带任何用户标识或统计
- **日历视图**（board 旧待办的归属问题就此结清：日历不在 M2 范围，占位页文案保持现状，是否做留给后续里程碑裁决）
